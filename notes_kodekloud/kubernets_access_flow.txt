# KUBERNETES ADMIN & SECURITY HANDBOOK: FROM ZERO TO PRODUCTION
# Focus: AWS EKS (Elastic Kubernetes Service) Implementation

--------------------------------------------------------------------------------
PART 1: THE INFRASTRUCTURE LIFECYCLE (THE ADMIN BLUEPRINT)
--------------------------------------------------------------------------------

As a Kubernetes Administrator, your responsibility spans the entire lifecycle: 
provisioning infrastructure, deploying applications, exposing them to the network, 
and securing access.

1. CLUSTER PROVISIONING (The Foundation)
   - Concept: Creating the Control Plane (Master) and Worker Nodes.
   - Tool: 'eksctl' (The industry standard for AWS EKS).
   - Command:
     $ eksctl create cluster --name my-prod-cluster --region us-east-1 --nodegroup-name workers --node-type t3.medium --nodes 2
   - Result: AWS provisions EC2 instances, sets up networking (VPC), and starts the Kubernetes Control Plane.
   - Admin Access:
     $ aws eks update-kubeconfig --name my-prod-cluster
     (This updates your local ~/.kube/config file to communicate with the new cluster).

2. APPLICATION DEPLOYMENT (The Workload)
   - Concept: Kubernetes does not run code directly; it runs Containers.
   - Prerequisite: Code must be containerized (Docker Image) and pushed to a registry (ECR/DockerHub).
   - The Manifest (Deployment.yaml):
     This defines "What to run" and "How many copies".
     
     apiVersion: apps/v1
     kind: Deployment
     metadata:
       name: my-web-app
     spec:
       replicas: 3               # High Availability (3 copies)
       selector:
         matchLabels:
           app: frontend         # CRITICAL: This label identifies these pods
       template:
         metadata:
           labels:
             app: frontend       # The actual label on the pod
         spec:
           containers:
           - name: my-app-container
             image: my-repo/my-app:v1

3. SERVICE NETWORKING (The Exposer)
   - Concept: Pods have dynamic IPs that change. A Service provides a static IP/DNS.
   - The Linking Logic: The Service finds Pods using "Selectors" that match the Pod's "Labels".
   - The Manifest (Service.yaml):
   
     apiVersion: v1
     kind: Service
     metadata:
       name: my-web-service
     spec:
       type: LoadBalancer        # Requests a Public IP from AWS
       selector:
         app: frontend           # MATCHING: Sends traffic to pods with this label
       ports:
         - port: 80              # Port exposed to the world
           targetPort: 80        # Port the container is listening on

--------------------------------------------------------------------------------
PART 2: THE ACCESS SECURITY MODEL (GATE vs. DOOR)
--------------------------------------------------------------------------------

Confusion often arises because access involves two distinct layers: Cloud Security and Cluster Security.

THE ANALOGY:
1. Level 1 (The Main Gate): AWS IAM (Identity & Access Management).
   - Verifies: "Is this person a valid employee?"
   - Result: Authentication (AuthN). You get into the building lobby.

2. Level 2 (The Office Door): Kubernetes RBAC (Role-Based Access Control).
   - Verifies: "Does this employee have the key to the Server Room?"
   - Result: Authorization (AuthZ). You get access to specific resources (Pods).

3. The Bridge (The Mapping): 'aws-auth' ConfigMap.
   - Function: Connects the AWS Identity (Gate) to the Kubernetes Identity (Door).
   - Without this, AWS knows you, but Kubernetes doesn't.

--------------------------------------------------------------------------------
PART 3: GRANTING USER ACCESS (STEP-BY-STEP WORKFLOW)
--------------------------------------------------------------------------------

Scenario: You need to grant a new developer, "Raju", read-only access to Pods.

STEP 1: IDENTITY CREATION (AWS LEVEL)
   - Action: Create an IAM User for Raju in the AWS Console.
   - Outcome: Raju gets an Access Key and Secret Key.
   - Status: Raju can authenticate with AWS, but cannot see any Kubernetes resources yet.

STEP 2: THE BRIDGE MAPPING (CRITICAL STEP)
   - Action: Map the AWS User to a generic Kubernetes Username.
   - Command: $ kubectl edit configmap aws-auth -n kube-system
   - Configuration to Add:
     
     mapUsers: |
       - userarn: arn:aws:iam::111122223333:user/raju   # The AWS Identity (Source)
         username: raju-k8s                              # The Internal K8s Name (Destination)
         groups:
           - system:basic-user

STEP 3: DEFINING PERMISSIONS (RBAC - THE ROLE)
   - Action: Create a "Rule Book" that defines what actions are allowed.
   - File: read-pods-role.yaml
     
     apiVersion: rbac.authorization.k8s.io/v1
     kind: Role
     metadata:
       namespace: default
       name: pod-viewer-role
     rules:
     - apiGroups: [""]
       resources: ["pods", "pods/log"]   # Can only touch Pods and Logs
       verbs: ["get", "list", "watch"]   # Can only Read (No delete/create)

STEP 4: ASSIGNING PERMISSIONS (RBAC - THE BINDING)
   - Action: Hand over the "Rule Book" to "Raju".
   - File: raju-binding.yaml
     
     apiVersion: rbac.authorization.k8s.io/v1
     kind: RoleBinding
     metadata:
       name: raju-read-access
       namespace: default
     subjects:
     - kind: User
       name: raju-k8s          # MUST MATCH the username defined in Step 2
       apiGroup: rbac.authorization.k8s.io
     roleRef:
       kind: Role
       name: pod-viewer-role   # The Role defined in Step 3
       apiGroup: rbac.authorization.k8s.io

--------------------------------------------------------------------------------
PART 4: THE REQUEST FLOW (UNDER THE HOOD)
--------------------------------------------------------------------------------

When Raju types `kubectl get pods`, the following chain reaction occurs:

1. Client: `kubectl` sends a request using Raju's AWS credentials.
2. AWS IAM (Gate): Confirms the credentials are valid. (AuthN Pass).
3. EKS Bridge: Checks `aws-auth`. Maps "AWS User Raju" -> "K8s User raju-k8s".
4. K8s RBAC (Door): Checks for RoleBindings for "raju-k8s".
5. Verification: Finds "raju-read-access" binding linked to "pod-viewer-role".
6. Result: Access Granted. Pod list is returned.

--------------------------------------------------------------------------------
PART 5: REVOKING ACCESS (OFFBOARDING)
--------------------------------------------------------------------------------

Method A: The Hard Stop (Recommended)
   - Action: Delete the IAM User in AWS Console.
   - Result: Authentication fails immediately. The user cannot even reach the cluster.

Method B: The Soft Stop
   - Action: Delete the RoleBinding in Kubernetes.
     $ kubectl delete rolebinding raju-read-access
   - Result: Authentication succeeds (user enters lobby), but Authorization fails ("Forbidden").

--------------------------------------------------------------------------------
ADMIN CHECKLIST FOR ACCESS ISSUES
--------------------------------------------------------------------------------
If a user gets "Access Denied" or "Unauthorized", check these three boxes:

[ ] 1. AWS IAM: Does the user exist in AWS and have CLI access?
[ ] 2. The Bridge: Is the user's ARN correctly mapped in the `aws-auth` ConfigMap?
[ ] 3. The Rules: Does a RoleBinding exist that links their mapped username to a Role?













# KUBERNETES KUBECONFIG HANDBOOK: THE ULTIMATE GUIDE
# Concept: Identity, Destination, and Mapping

--------------------------------------------------------------------------------
PART 1: WHAT IS A KUBECONFIG FILE?
--------------------------------------------------------------------------------

The Kubeconfig file serves two primary purposes for the `kubectl` command-line tool:
1. The Map (Destination): Where is the cluster located? (API Server URL).
2. The ID Card (Authentication): Who are you? (Certificates/Tokens).

Without this file, `kubectl` is just a tool with no direction. It doesn't know 
which server to talk to or which credentials to present.

Standard Location: ~/.kube/config (Linux/Mac) or %USERPROFILE%\.kube\config (Windows).

--------------------------------------------------------------------------------
PART 2: ANATOMY OF THE FILE (THE 3 PILLARS)
--------------------------------------------------------------------------------

A Kubeconfig file is divided into three distinct sections. Understanding how they 
interact is the key to mastering Kubernetes access.

1. CLUSTERS (The Destination)
   - Defines: "Where do I go?"
   - Contains:
     * server: The API Server URL (e.g., https://10.0.0.1:6443).
     * certificate-authority: The Root CA file to trust the server (SSL).
   - Note: This is usually common for all developers working on the same project.

2. USERS (The Identity)
   - Defines: "Who am I?"
   - Contains:
     * client-certificate / client-key: For manual setup.
     * token: For Service Accounts.
     * exec (command): For Cloud (AWS/GCP) to dynamically fetch tokens.
   - Note: This is unique to YOU. Your file has your keys; your colleague's file 
     has their keys.

3. CONTEXTS (The Mapping)
   - Defines: "Which User goes to which Cluster?"
   - The Formula: Context = Cluster + User + [Namespace (Optional)]
   - Purpose: Allows you to switch between environments (Dev, Prod, Test) 
     without typing credentials every time.

--------------------------------------------------------------------------------
PART 3: SAMPLE STRUCTURE (VISUALIZATION)
--------------------------------------------------------------------------------

apiVersion: v1
kind: Config
clusters:
- name: production-cluster      # Destination A
  cluster:
    server: https://1.2.3.4:6443
    certificate-authority: /path/to/ca.crt
- name: dev-cluster             # Destination B
  cluster:
    server: https://5.6.7.8:6443
    insecure-skip-tls-verify: true

users:
- name: admin-user              # Identity A
  user:
    client-certificate: /path/to/admin.crt
    client-key: /path/to/admin.key
- name: developer-user          # Identity B
  user:
    token: "secure-token-123"

contexts:
- name: prod-admin-ctx          # Mapping 1
  context:
    cluster: production-cluster
    user: admin-user
- name: dev-view-ctx            # Mapping 2
  context:
    cluster: dev-cluster
    user: developer-user
    namespace: backend          # PRO TIP: Default namespace

current-context: prod-admin-ctx # The Active Profile

--------------------------------------------------------------------------------
PART 4: MASTERING CONTEXT SWITCHING
--------------------------------------------------------------------------------

You never manually edit the file to switch clusters. You use commands.

1. View all available environments:
   $ kubectl config get-contexts

2. Switch to a different environment (e.g., from Dev to Prod):
   $ kubectl config use-context prod-admin-ctx
   (Now all subsequent commands will go to the Production Cluster).

3. Set a default Namespace (The Pro Tip):
   Stop typing `-n my-namespace` every time.
   $ kubectl config set-context --current --namespace=my-namespace

--------------------------------------------------------------------------------
PART 5: HOW KUBECONFIG IS APPLIED
--------------------------------------------------------------------------------

A common misconception is that you need to run `kubectl apply` for config files. 
You do NOT. Kubeconfig is a client-side setting, not a cluster resource.

Priority Order (How kubectl finds the file):
1. The Flag: `kubectl get pods --kubeconfig=myfile.yaml` (Highest priority, temporary).
2. Env Variable: `export KUBECONFIG=/path/to/myfile.yaml` (Session priority).
3. Default Path: `~/.kube/config` (Lowest priority, permanent).

To "Merge" files (e.g., you have 3 separate config files):
   $ export KUBECONFIG=~/.kube/config:~/.kube/config-2:~/.kube/config-3
   $ kubectl config view --flatten > ~/.kube/merged-config

--------------------------------------------------------------------------------
PART 6: CLOUD VS. ON-PREMISE DIFFERENCES
--------------------------------------------------------------------------------

Scenario A: On-Premise (Manual)
   - You receive a physical file (or certs) from the Admin.
   - You must manually place it in `~/.kube/config`.
   - Authentication relies on Static Certificates/Tokens inside the file.

Scenario B: Cloud (AWS EKS / GKE / AKS)
   - You do not create the file manually.
   - You run a CLI command: `aws eks update-kubeconfig --name my-cluster`.
   - The file is auto-generated.
   - Authentication relies on the "exec" plugin (it calls the AWS CLI in the 
     background to get a temporary token).

--------------------------------------------------------------------------------
PART 7: SECURITY BEST PRACTICES
--------------------------------------------------------------------------------

1. Never commit kubeconfig to Git: It often contains private keys or tokens. 
   Possession of this file equals possession of your identity.
   
2. Revocation:
   - You cannot "delete" a kubeconfig from a user's laptop remotely.
   - To revoke access, you must delete the RoleBinding (RBAC) in the cluster.
   - Even if the user has the file, the cluster will reject their actions 
     ("Forbidden").

3. The "Current Context" Risk:
   - Always check your context before running delete commands.
   - Use tools like `kubectx` or prompt plugins to display the active cluster 
     in your terminal.
