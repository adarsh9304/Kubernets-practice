kubernets does not deploy containers directly on the worker node. containers are encapsulated into kubernets object known as pods.
A pod is a single instance of an application. a pod is a smallest object you can create in kubernets

pods usually have one to one relationship with container running out application. to scale up we create new pods and to scale down we delete the existing pod. we do not add additional container to an existing pod to scale out app

a single pod can have multiple containers except for the fact they are usually not multiple containers of the same type. but in some cases me might require helper container that doing some kind of supportive task like processing of user entered data, file upload by user etc...


when we run 
    kubectl run nginx --image nginx
it first creates a pod automatically and deploys an instance of the nginx docker image. the image downloaded from docker hub repository

The replication controller helps us run multiple instances of a single pod in kubernet cluster, thus providing high availability 
the replication controller ensures that specific number of pods running at all times 
another reason we need replication controller is to create multiple pods to share the loads across them 

replication controller is older technology that is being replaced by replicaSet 

in the spec we mention template under which we provide pod template. inside that we will mention properties for pod 


The role of the replicaSet is to monitor the pods, if any of them were to fail, deploy new ones. we can use it to monitor exisitng pods if we have them already. now how replicaset would know which pod to monitor? for that we need to mention match label 
selector:
    matchLabels:
        tier: front-end


let's say we have already a pods and wants monitoring from replicaSet, in that case also we require to put template section beacuse suppose any of them falls then replicaSet should have template from which it can make new pod

kubectl get replicaset 

replicaset will not allow more pods with the same label than the number of replicas configured on the replicaset 

suppose we want to update the replicas count then we will run this command: 
    kubectl edit replicaset myapp-replicaset (name of our replica)

    when we run above command it's opens up the running configuration of the replicaSet in a text editor in a text format, it is basically temporary file that's created by kubernets in memory to allow us to edit the configuration of an exisitng object on kubernets 

    through terminal also we can do this with the help of scale parameter 

    kubectl scale replicaset myapp-replicaset --replicas=2

    for detail conceptual: kubectl explain replicaset

when we create a deployment, it triggers rollout, a new rollout creates a new deployment revision, let's call it revision 1 

we can see the status of our rollout by running the command 
    kubectl rollout status deployment/myapp-deployment 

To see the revision and history of rollout run the command:
    kubectl rollout history deployment/myapp-deployment 

There are two types of deployment strategies 
    one way is to destroy all of these and then create newer versions of application instances, meaning first destroy the five running instances and then deploy five new instances of the new application version, one problem with this strategy is that during the period after the older versions are down and before any new version is up the application is down and inaccessible to users, this strategy is known as recreate strategy 

    in the second strategy we do not destroy all of them at once. instead, we take down the older version and bring up a newer version one by one. this way app never goes down and upgrade is seamless. it is rolling update
    and rolling update is the default deployment strategy

    after rollout if we run the command 
        kubectl get replicas 
        we will have 2 replicaset, one will have zero pods and second will have all pods which indicate one is down and second is up for all instances 


Kubernetes allow us to roll back to a previous revision, to undo a change, run this command
    kubectl rollout undo deployment myapp-deployment 

we will run the command with --record to see the logs in the history 
    kubectl create -f deployment-defination.yml --record
