in the docker world IP address is always assigned to a docker container where as in kubernets IP address is assigned to a pod, each pod in the kubernets gets its own internal IP address 

when kubernets is initially configured, we create an internal private network with the address suppose 10.244.0.0 and all pods are attached to it 
when we deploy multiple pods, they all get a seperate IP assigned from this network, the pods can communicate to each other through this IP, but accesssing the other pods using this internal IP address may not be good idea as it's subject to change when pods are recreated

let's take example, we have two nodes running kubernets and they have IP addresses 192.168.1.2 and 192.168.1.3 assigned to them, and they are not part of cluster yet, each of them has a single pod deployed, these pods are attached to an internal network and they have their own IP addresses assgined, if we look internal network they are same, two networks have an same address 10.244.0.0 and the pods deployed have the same address too, this is not going to work wll when the nodes are part of the same cluster, the pods have the same IP addresses assigned to them that will lead to IP conflict in the network, that's one problem


when a kubernets cluster is set up, kubernets dows not automatically set up any kind of networking to handle these issues

    kubernets expects us to set up networking to meet certain fundamental requirements like 
    All the containers or pods in a kubernets cluster must be able to communicate with one other without having to configure NAT, all nodes must be able communicate with containers and all containers must be able to able to communicates with the nodes in the cluster, kubernets expects us to setup a networking solutions

we have prebuild solutions for that like cisco aci network, cillium, big cloud fabric, flannel , calico etc...
this create a virtual network of all pods and nodes where they are all assigned unique ip address 



let's say we deployed our pod, having web app running on it, how do we as an external user access the webpage?
     the first option is that SSH into kubernets node and then we would be able to access the pods webpage by doing a curl, this is from inside the kubernets node and that's not really we want, we want to be able to access the web server from our own laptop without having to SSH into the node 

     this is where the kubernets service comes into play. it is kind object just like pods, replicaset and deployments. one of it's usecase is to listen to a port on the node and forward the request on that port to a port on the pod running, this kind of service is known as nodeport 

     the port on the pod where the actual web server is running referred as target port, the second port is the port on the service itself, it is referred as port, these items are from the viewpoint of service, the service is like a virtual server inside the node, and finally we have port on the node itself, which we use to access the web server externally and that is called nodeport and range of nodeport is 30,000 to 32,767

    if we don't provide target port it is assumed to be same as port, and if we don't provide a node port then any random port from the range would be assigned 

    here we are mentioning target port but not mentioning target port on which pod, there could be hundreds of other pods with web service running on port 80, in this we can use selectors 

    we know that the pod created with label, we need to bring that label into the service defination file 

    when the service is created it looks for a matching pod with the labels and finds all the instances/repliacas of the app, for distribution it uses random algorithm

Kubernets service can help us group the pods together and provides a single interface to access the pod in a group, suppose service created for backend pods together and provide a single interface to access the pods in a group, the requests are forwarded to one of the pods under the service randomely 

each service gets an IP and name assigned to it inside the cluster and that is the name that should be used by other pods to access the service, this type of service is known as clusterIP. it is default type 
to link the service to a set of pods we use selectors
