====================================================================
              KUBERNETES STORAGE: THE COMPLETE GUIDE
====================================================================

1. THE CORE PROBLEM: WHY DO WE NEED STORAGE IN K8S?
--------------------------------------------------------------------
* Pods are "ephemeral" (temporary).
* If a Pod crashes, gets deleted, or is moved to another Node, all data inside it is wiped out.
* Databases (MySQL, Postgres) and file servers need data to persist.
* Solution: Decouple (separate) storage from the Pod's lifecycle. If the Pod dies, the storage remains safe.


2. THE 4 MAIN PILLARS OF KUBERNETES STORAGE
--------------------------------------------------------------------

A. VOLUMES (The Basic Level)
Tied to the Pod's lifecycle. Used for basic use-cases.
* emptyDir: A temporary empty directory. Used for sharing data between containers inside the SAME Pod. Gets deleted when the Pod is deleted.
* hostPath: Mounts a file/directory from the physical Node's filesystem. 
  - Risk: If the Pod moves to a different Node, it loses access to that data. Not recommended for production.

B. PERSISTENT VOLUMES (PV) - "The Physical Storage"
* Represents the actual physical storage in your cluster (e.g., AWS EBS, Google Persistent Disk, NFS).
* It is a Cluster-level resource (not bound to any specific namespace).
* Exists independently of any Pod.
* Usually created manually by a K8s Administrator (Static Provisioning).

C. PERSISTENT VOLUME CLAIMS (PVC) - "The Request"
* A request made by a Developer for storage.
* Example: "I need 10GB of storage with ReadWriteOnce access."
* K8s looks for an available PV that matches this request and "Binds" them together.
* The Pod then mounts the PVC, not the PV directly. Developers don't need to know the underlying infrastructure.

D. STORAGE CLASSES (SC) - "The Automation Engine"
* Manually creating PVs for every PVC request is tedious. StorageClasses solve this via "Dynamic Provisioning".
* An Admin creates a StorageClass template (e.g., "fast-ssd").
* When a Developer creates a PVC and mentions this StorageClass, K8s automatically talks to the Cloud Provider (AWS/GCP), creates the physical hard drive, creates the PV, and binds it to the PVC.


3. CONTAINER STORAGE INTERFACE (CSI)
--------------------------------------------------------------------
* The modern standard for K8s storage.
* Previously, storage code (AWS, Azure plugins) was hardcoded inside the K8s source code ("in-tree"). 
* CSI allows storage vendors (NetApp, AWS, PureStorage) to write external plugins. K8s uses the CSI standard to communicate with any external storage seamlessly.


4. THE END-TO-END WORKFLOW (Dynamic Provisioning)
--------------------------------------------------------------------
Step 1: Admin creates a StorageClass.
Step 2: Developer applies a PVC yaml file requesting 10GB storage.
Step 3: StorageClass detects the PVC and automatically provisions a 10GB disk in the cloud.
Step 4: StorageClass automatically creates a PV and binds it to the PVC.
Step 5: Developer creates a Pod and mounts the PVC as a volume.
* Result: If the Pod dies, K8s spins up a new Pod, attaches the exact same PVC, and no data is lost!


====================================================================
                      QUICK YAML EXAMPLES
====================================================================

# 1. THE PVC (Developer requests 5GB of storage)
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-app-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: standard

---

# 2. THE POD (Mounting the PVC)
apiVersion: v1
kind: Pod
metadata:
  name: my-app-pod
spec:
  containers:
    - name: nginx
      image: nginx
      volumeMounts:
        - mountPath: "/var/www/html"   # Where data goes inside container
          name: my-storage-volume
  volumes:
    - name: my-storage-volume
      persistentVolumeClaim:
        claimName: my-app-pvc          # Linking to the PVC created above









====================================================================
            KUBERNETES STATEFULSETS: THE COMPLETE GUIDE
====================================================================

1. THE PROBLEM: WHY NOT USE "DEPLOYMENTS" FOR DATABASES?
--------------------------------------------------------------------
* Deployments are meant for STATELESS applications (like web servers).
* In a Deployment, Pods are treated as identical clones. 
* If a Deployment Pod dies, a new one spins up with a random name (e.g., myapp-84b5dfg) and no memory of what it was doing.
* Databases (like MySQL, MongoDB, Kafka) are STATEFUL. They need:
  1. A fixed identity (so Primary and Replica nodes know who is who).
  2. To keep their specific data even if the Pod restarts.
  3. Ordered startup and shutdown (e.g., Primary must start before Replicas).


2. WHAT IS A STATEFULSET?
--------------------------------------------------------------------
* A StatefulSet is the K8s workload API object used to manage stateful applications.
* It manages the deployment and scaling of a set of Pods, and guarantees the ordering and uniqueness of these Pods.
* Simply put: It is the standard and safest way to run databases in Kubernetes.


3. CORE FEATURES (The "Sticky" Identity)
--------------------------------------------------------------------
A. STABLE, UNIQUE NETWORK ID
* Unlike Deployments (which use random hashes), StatefulSet Pods get a predictable, sequential name.
* Example: If your StatefulSet is named "mysql", Pods will be named:
  - mysql-0 (Usually the Primary)
  - mysql-1 (Replica 1)
  - mysql-2 (Replica 2)
* If "mysql-1" crashes, K8s will spin up a new Pod with the EXACT same name: "mysql-1".

B. ORDERED DEPLOYMENT & SCALING
* Pods are created one by one, in order (0, then 1, then 2). 
* K8s waits for "mysql-0" to be completely running and ready before starting "mysql-1".
* When scaling down (or deleting), they terminate in reverse order (2, then 1, then 0).

C. HEADLESS SERVICE
* StatefulSets require a "Headless Service" (a K8s Service with ClusterIP set to 'None').
* Instead of load-balancing traffic randomly across Pods, a Headless Service creates DNS records for EACH individual Pod.
* This allows "mysql-1" to talk directly to "mysql-0" to sync database records.


4. THE MAGIC: "volumeClaimTemplates" (Storage Link)
--------------------------------------------------------------------
* If you put a normal PVC inside a Deployment, all 3 Pod replicas would try to read/write to the exact same disk (Data corruption!).
* StatefulSets use a feature called "volumeClaimTemplates".
* Instead of sharing one disk, the StatefulSet automatically creates a BRAND NEW PVC (and physical PV) for EVERY individual Pod.
* "mysql-0" gets its own 10GB disk.
* "mysql-1" gets its own 10GB disk.
* If "mysql-1" dies and is recreated, K8s automatically re-attaches it to its specific 10GB disk. No data is lost!


====================================================================
                      QUICK YAML EXAMPLES
====================================================================

# 1. THE HEADLESS SERVICE
apiVersion: v1
kind: Service
metadata:
  name: nginx-db-service
spec:
  clusterIP: None       # This makes it a "Headless" Service
  selector:
    app: nginx-db
  ports:
    - port: 80

---

# 2. THE STATEFULSET
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web-db
spec:
  serviceName: "nginx-db-service"  # Links to the headless service above
  replicas: 3
  selector:
    matchLabels:
      app: nginx-db
  template:
    metadata:
      labels:
        app: nginx-db
    spec:
      containers:
      - name: nginx
        image: nginx
        volumeMounts:
        - name: db-storage         # Matches the template name below
          mountPath: /usr/share/nginx/html

  # The Magic: Automatically creates a PVC for each Pod (web-db-0, web-db-1, etc.)
  volumeClaimTemplates:
  - metadata:
      name: db-storage
    spec:
      accessModes: [ "ReadWriteOnce" ]
      resources:
        requests:
          storage: 5Gi
      storageClassName: standard
